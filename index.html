Sign In Once. Every Sibling App Offers One Tap.

flutter_sso shares saved sign-ins between the apps of one company. It stores and returns them. It does not sign anyone in — your app still does that.

Channel flutter_sso/keychain
Record schema v3
Rule share a proof, never a session
01

What It Is

Is

A saved sign-in

One record on the phone. It holds a proof of who the user is, plus a name and email to draw a card.

Is not

A shared session

No access token. No refresh token. Two apps holding one token pair looks exactly like a stolen token.

Is not

An auth client

No server calls. No browser. No OAuth. No redirect URLs anywhere in the package.

03

Naming the Group

Runner.entitlements
<key>keychain-access-groups</key>
<array>
  <string>$(AppIdentifierPrefix)com.example.sso.shared</string>
</array>
Info.plist — what Dart reads
<key>SsoSharedKeychainGroup</key>
<string>$(DEVELOPMENT_TEAM).com.example.sso.shared</string>

The one-character trap. $(AppIdentifierPrefix) ends in a dot. $(DEVELOPMENT_TEAM) does not, so add your own. Miss it and every read returns -34018. Neither file warns you.

Ten-second check. Run the app and look for the group: log line. If it is not the full resolved string, Team ID included, stop. Nothing else can work.

Or skip both files and pass SsoConfig.sharedAccessGroup directly. Both apps must end up with the same string.

App data belongs to the app's own Linux user, and its Keystore key is tied to that user. A sibling app cannot read your file, and could not decrypt it if it could. So we ask it instead — and the lock is the caller's signing certificate, checked on every call.

Door methodWhat the receiver does
readAnswers with its own record plus every slot — not just what it signed in with.
writeFiles it as a slot under the caller's package name. Capped at 256 KB.
removeDrops one account, but only if the schema version matches.
clearDrops the record and every slot.

Exported, and on purpose without a signature permission. That needs both apps signed with one key. Two apps on Play App Signing never are. The check happens inside call() instead.

Why read includes slots: an app that only ever tapped "Continue as" holds the account in a slot. Answer with the own record alone and uninstalling one app takes the whole family's sign-ins with it.

04

The Code, in Order

1 · sign-in screen — offer what is saved
if (!store.isSupported) return [];        // hide the sharing UI

final saved = await store.read();
for (final c in saved) {
  if (!c.isUsable) continue;               // half a credential is none
  showCard(
    name:       c.profile.name,          // safe to draw
    from:       c.origin,                // "saved by xyz"
    activeHere: c.isActiveIn('abc'),     // already signed in here?
  );
}
2 · password login — secret BEFORE the API call
final deviceSecret = await store.getDeviceSecret();
final result = await api.login(email, password, deviceSecret: deviceSecret);

await store.save(SsoCredential(
  userId:  result.userId,
  secret:  SsoSecret(token: result.idToken),
  profile: SsoProfile(name: result.name, email: result.email),
));
3 · one-tap — trade the saved proof
final session = await api.exchange(
  idToken:      card.secret.token,
  deviceSecret: card.secret.deviceSecret,   // filled in by save()
);
await store.setActive(userId: card.userId, isActive: true);
4 · sign out, reject, forget
await store.setActive(userId: id, isActive: false);  // keeps the card
await store.remove(id);                              // server said no
await store.clear();                                // user said no

The one ordering rule. getDeviceSecret() must run before your auth API call. A secret made after the token exists cannot be tied to it, and the sibling app's exchange will fail.

SsoExceptioncode, message, isRetryable.Retry when isRetryable. Never sign the user out on it.
SsoLogOne tag: sso.Set SsoLog.sink to forward to Crashlytics or Sentry.

isUsable is true only when both halves of the secret are present. Skip any card where it is false — half a credential cannot be traded.

Before You Ship

01
Order. getDeviceSecret() runs before the auth API call, on both apps.
REQUIRED
02
iOS group. The group: log line shows the full resolved string on a real device, in a release build.
REQUIRED
03
Android trust. Release builds list both apps' SHA-256 app-signing digests, not self, not the upload key.
REQUIRED
04
Late install. Sign in on app A, then install app B and cold-launch it. This is the only IPC path.
REQUIRED
05
Sign-out sticks. Sign out of B, relaunch B: card shows, session does not come back.
REQUIRED
06
Removal sticks. Reject a token, then relaunch both apps. The dead card must not return.
REQUIRED
07
Nothing leaks. Grep the logs for the token and the secret. You should only ever see sizes.
BLOCK IF FAIL
08
Fallback. Break the group or the digest on purpose. The plain sign-in form must still work.
BLOCK IF FAIL
